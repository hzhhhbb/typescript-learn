进阶类型：类型编程

React 的 useState、Express 的类型推导、你遇到的每个库的类型定义——背后都是这些技巧。这课是 TS 独有的"类型编程"：keyof、映射类型、条件类型、infer。C# 完全没有对应物，但它们是读懂现代库代码的钥匙。

⏱ 15-20 分钟

为什么学这个？

你已经在用工具类型了，只是不知道。全栈代码里这些写法无处不在：

// 真实代码里的样子（你以前可能看不懂）
type CreateTodoInput = Omit<Todo, "id" | "done">;  // 去掉两个键
type Config = Partial<FullConfig>;                 // 全部变可选
type Result = ReturnType<typeof fetchUser>;          // 函数返回类型
全新概念 这些不是运行时库——是类型层面的操作：对"类型"做变换，产生新"类型"。它们编译后完全消失（第一课的擦除在这里体现到极致）。C# 里没有"对类型做运算"的能力（反射是运行时的，做不到编译期推导）。

基础一：keyof + 索引访问

interface Todo { id: number; title: string; done: boolean; }

type TodoKeys = keyof Todo;        // "id" | "title" | "done"（键的联合）
type Title = Todo["title"];       // string（索引访问：取属性类型）

const k: TodoKeys = "title";  // ✓
k = "other";                       // ✗ TS2322
你已经知道 keyof ≈ C# 反射里 GetProperties() 的属性名集合——但 keyof 在编译期完成且类型安全（C# 反射是运行时字符串）。keyof 联合类型还能配合第三课的收窄用。
逐步推导：keyof 和索引访问
  1. 起点：interface Todo { id: number; title: string; done: boolean; } 描述"有三个键的对象"。
  2. 提取键：keyof Todo = "Todo 的所有键" = "id" | "title" | "done"（字面量联合——第三课）。
  3. 取属性类型：Todo["title"] = "title 键对应的类型" = string。把 JS 运行时 todo["title"]（取值）搬到类型层面（取类型）。
  4. 为什么有用：K 可以是动态的。function getProp<T, K extends keyof T>(obj: T, key: K): T[K] 里，传 "title" 返回 string、传 "id" 返回 number——返回类型跟着键走（C# 反射做不到编译期检查）。

基础二：映射类型

{ [K in keyof T]: ... } 遍历每个键、逐个变换——类型层面的 map：

type OptionalTodo = { [K in keyof Todo]?: Todo[K] };  // 全部变可选
type ReadonlyTodo = { readonly [K in keyof Todo]: Todo[K] };  // 全部只读
逐步推导：{ [K in keyof Todo]?: Todo[K] }
  1. 先算 keyof Todo = "id" | "title" | "done"（上一步）。
  2. 读 [K in ...] = "对联合里的每个值 K，生成一个属性"。
  3. 依次代入展开： 
    K = "id"    → id:    Todo["id"]    → id:    number
K = "title" → title: Todo["title"] → title: string
K = "done"  → done:  Todo["done"]  → done:  boolean
  4. 加 ?: 修饰符：每个属性变可选。
结果 = { id?: number; title?: string; done?: boolean }
C# 类比 todos.Select(t => new { t.id, t.title })——对集合每个元素做变换得到新集合。映射类型就是对"键的联合"的每个键做变换，得到新类型。

内置工具类型：全栈代码高频出现

TS 内置了常用变换，直接可用（都在 lib 里，零引入）：

工具类型作用示例
Partial<T>所有属性变可选表单编辑：Partial<User> 更新部分字段
Required<T>所有属性变必选补齐可选配置
Readonly<T>所有属性只读不可变配置对象
Pick<T, K>只保留指定键Pick<Todo, "id"> 轻量视图
Omit<T, K>去掉指定键Omit<Todo, "id"> 创建输入（第十课的 CreateTodoInput 就是它！）
Record<K, V>键值对象类型Record<Status, string> 按状态存文案
ReturnType<F>函数返回类型从 API 函数推导响应类型
Awaited<T>取 Promise 内部类型Awaited<Promise<User>> = User
对照第十课：CreateTodoInput 我们手写了两个字段——其实一行 Omit<Todo, "id" | "done"> 就能表达"Todo 减去服务器生成的字段"。类型先行 + 工具类型组合，是真实项目的常见风格。
工具类型不神秘：官方实现就是映射类型
// TypeScript 官方 lib 里的真实定义
type Partial<T>    = { [P in keyof T]?: T[P] };          // 全部可选
type Required<T>   = { [P in keyof T]-?: T[P] };         // 全部必选（-? 去掉可选）
type Readonly<T>   = { readonly [P in keyof T]: T[P] };   // 全部只读
  1. Partial<Todo> = 遍历 Todo 的键、每个加 ?——和上面的 OptionalTodo 推导一模一样。
  2. Pick<T, K> / Omit<T, K> = 遍历时只保留 / 排除 K 里的键（K 是"选中的键"联合）。
  3. 所以你在代码里见到的 Partial<User>、Omit<Todo, "id">——都是预写好的映射类型，不是魔法。

条件类型 + infer：类型层面的逻辑

// 条件类型：T extends U ? X : Y（if/else）
type IsString<T> = T extends string ? true : false;
type A = IsString<"hi">;  // true
type B = IsString<42>;   // false

// infer：从类型里"解出"子类型（C# 完全没有）
type ElementType<T> = T extends (infer U)[] ? U : never;
type E1 = ElementType<string[]>;  // string（解出数组元素类型）
type E2 = ElementType<number[]>;  // number
全新概念 infer：在条件类型里"声明一个待推导的类型变量"。TS 看 T extends (infer U)[] 时，会尝试把 T 匹配成"某数组"，成功就把元素类型赋给 U。内置的 ReturnType 就是这么实现的：T extends (...args: any) => infer R ? R : never。
逐步推导：条件类型和 infer
  1. 条件类型 = 类型层面的三元：T extends U ? X : Y —— "T 是不是 U 的子类型（T 能赋给 U 吗）？是取 X，否则取 Y"。和 C# 的 cond ? a : b 同一个形状。
  2. 代入 IsString<"hi">：把 T = "hi" 代入 → "hi" extends string ? true : false → "hi" 能赋给 string → true
  3. 代入 IsString<42>：42 extends string ? → 42 不是 string → false
  4. infer = var 的反面：var x = 42 是"写值，编译器猜类型"；infer U 是"写出模式，编译器解出类型变量"。C# 没有后者。
  5. 推导 ElementType<string[]>：把 T = string[] 和 (infer U)[] 匹配 → "string[] 是某个 U 的数组？是！U = string" → string
  6. 推导 ElementType<number>：number 不是数组，匹配失败 → never

实战：从 API 函数推导类型

function fetchUser(id: number): Promise<{ id: number; name: string }> {
  return Promise.resolve({ id, name: `User ${id}` });
}

type FetchResult = ReturnType<typeof fetchUser>; // Promise<{...}>
type User = Awaited<FetchResult>;              // { id: number; name: string }

// 改 fetchUser 的返回类型 → User 自动跟着变（改一处，全链路同步）
这是"修改一处、编译器帮你同步所有依赖类型"的极致：API 函数的返回类型一变，所有引用 User 的地方自动更新。C# 里需要手动维护 DTO 类，TS 里类型可以从源头推导。
逐步推导：ReturnType 和 Awaited
  1. 官方定义：type ReturnType<T> = T extends (...args: any[]) => infer R ? R : any;
  2. 代入：fetchUser 的类型 = (id: number) => Promise<{...}>。它匹配函数形状吗？是。R = 返回类型 = Promise<{ id: number; name: string }>。
  3. 再取一层：Awaited<Promise<User>> 从 Promise 里解出内部类型 = User（官方实现也用了 infer：T extends Promise<infer U> ? Awaited<U> : T，递归解包）。
  4. 链的威力：改 fetchUser 的返回类型 → User 自动跟着变，所有用 User 的地方同步更新。

一条链：把四个工具串起来

keyof（取键） → T[K]（取属性类型） → [K in keyof T]（遍历键变换 = 工具类型）
                                          ↓
                              T extends U ? X : Y（类型层面判断）
                                          ↓
                              infer（从模式解出类型 = ReturnType）

这四个工具组合起来，就是 TS 里几乎所有"看起来魔法"的类型推导。下次看到一个吓人的类型（比如 ReturnType<typeof useStore>），就沿着这条链拆开看：先找 keyof，再找映射，最后找 infer。

检查你的理解

Q1 · keyof

  • "id" | "title" | "done"
  • number
  • Todo 的构造函数
  • 任意字符串
keyof 提取对象类型的键为字面量联合类型。配合第三课收窄可用于类型安全的对象操作。

Q2 · 工具类型

  • 所有属性变可选
  • 所有属性变必选
  • 删除全部属性
  • 所有属性变只读
Partial 把所有属性标记为可选——常见于"部分更新"场景。Required 是它的反面，Readonly 是只读版本。

Q3 · infer

  • string
  • string[]
  • never
  • any
infer U 从数组类型中解出元素类型。内置 ReturnType 用它提取函数返回类型，Awaited 用它取 Promise 内部类型。

Q4 · 类型编程的运行时

  • 完全不存在，编译后擦除
  • 保留在产物中
  • 只在开发模式存在
  • 由 Node 运行时提供
类型编程是纯编译期操作（第一课的擦除在这里体现到极致）。实测：1.7KB 的类型源码编译后只剩 544 字节运行时逻辑。C# 里做不到——反射是运行时的。
