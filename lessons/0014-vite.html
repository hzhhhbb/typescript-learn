Vite 构建工具

为什么前端代码不能直接扔给浏览器？因为浏览器不认识 TS、不认识 import 的 npm 包、不会从 node_modules 找依赖。Vite 解决这个——开发时当"翻译服务器"，发布时当"打包器"。这课之后，你能看懂任何现代前端项目的启动命令。

⏱ 15-20 分钟

问题：浏览器读不了你的源码

你的 TS 前端代码有三个浏览器搞不定的地方：

  1. TS 语法：浏览器只执行 JS，不认识 : string 和 JSX（第一课的回声）
  2. import 包名：import { add } from "lodash"——浏览器不知道 "lodash" 是 node_modules 里的哪个文件（它只认相对路径 URL）
  3. 模块组织：几十个文件、嵌套依赖、CSS、图片——浏览器不会自己拼
全新概念 构建工具（Vite 是其中之一）干两件事：开发时把源码翻译成浏览器能吃的格式并实时提供；发布时把所有文件合并压缩成可部署的静态产物。

模式一：开发时 —— 翻译服务器

npm run dev 启动一个本地服务器（默认 localhost:5173）：

浏览器请求 /src/main.ts
// 你在源码里写的是 TS
import { setupCounter } from "./counter.ts";

// 浏览器收到的响应是 JS（esbuild 实时转译）
import { setupCounter } from "/src/counter.ts";
document.querySelector(...).innerHTML = `...`;
C# 对照：Razor 视图请求时渲染
// ASP.NET 的 Razor 页面在请求时编译渲染
// 类似"按需转换"：请求到了才处理
// 但 Vite 转的是 TS→JS，Razor 渲染的是 HTML
全新概念 按需转换：Vite 不预先编译所有文件——浏览器请求哪个文件，它才转哪个（启动 80ms 就能用）。转译用 esbuild（极快的 Go 编译器）。

杀手锏：HMR（热更新）

全新概念 HMR（Hot Module Replacement，热更新）：改代码保存后，浏览器只更新改动的那部分——不刷新页面、不丢状态（比如表单里打了一半的字不会被清掉）。C# 的 dotnet watch 是整页刷新，HMR 精细得多。

模式二：发布时 —— 打包器

npm run build 把整个应用打包成 dist/ 静态文件。我实测的产物：

$ npm run build
vite v8.2.1 building client environment for production...
✓ 9 modules transformed.
dist/index.html                  0.45 kB │ gzip: 0.29 kB
dist/assets/index-Na4_thdC.js    4.49 kB │ gzip: 2.02 kB   ← 你的 TS 全被压进这里
dist/assets/index-CsUDhMuy.css   4.10 kB │ gzip: 1.46 kB
✓ built in 305ms
  • 几十个 TS 文件 → 少量 JS/CSS（带内容哈希文件名，浏览器缓存友好）
  • 产物是纯静态文件——扔给 Nginx/CDN/任何静态服务器就能跑，不需要 Node
  • gzip 体积自动报告（2KB 的 JS，压缩后 2KB 不到）
你已经知道 和 C# 的发布类似：开发时一堆源文件，发布时一个包。区别：C# 发布要 IIS 运行 .NET；Vite 的产物是浏览器直接吃的静态文件，不需要任何运行时。

关键认知：Vite 和 tsc 的分工

打开 demo-vite 的 package.json，看 build 脚本：

"build": "tsc && vite build"   // 先 tsc，再 vite
分工明确：tsc 负责类型检查（你的类型安全），vite build 负责打包（转译 + 合并 + 压缩）。Vite 自己不做类型检查（esbuild 只转译不检查）——所以生产构建前先跑 tsc 把关。两个工具各管各的，这和我们第一课讲的一致：类型是编译期概念。

动手练习

在 code/ 里验证（5 分钟）

我建好了 code/demo-vite/（vanilla-ts 模板，已验证）。做几件事：

  1. cd code/demo-vite && npm run dev——启动 dev server，浏览器打开 localhost:5173，看到页面。
  2. 挑战 1：打开 src/counter.ts，把按钮文字改一下保存——看页面不刷新就更新了（HMR 生效）。
  3. 挑战 2：在浏览器 DevTools 的 Network 面板，刷新页面，点开 main.ts 的请求——看到响应是 JS 不是 TS（按需转换的证据）。
  4. 挑战 3：npm run build，然后 npm run preview——localhost:4173 打开的是 dist/ 产物（发布后的样子）。

检查你的理解

Q1 · 按需转换

  • 浏览器请求时才转
  • 启动时全部转好
  • 编译一次永久生效
  • 从不转换直接执行
Vite 按需转换：浏览器请求哪个文件才转哪个（esbuild 转译，启动只要 80ms）。你在 Network 面板能看到响应是 JS 不是 TS。

Q2 · HMR

  • 即时更新且不刷新页面
  • 整页重新加载
  • 需要手动刷新才生效
  • 只重新编译不更新
HMR 只替换改动的那部分模块——不刷新、不丢状态（表单里打了一半的字还在）。比 dotnet watch 的整页刷新精细。

Q3 · 打包产物

  • 可直接部署的静态文件
  • TS 源码的副本
  • 需要 Node 的中间文件
  • 压缩后的源码包
dist/ 是纯静态文件（HTML + 打包好的 JS/CSS），扔给 Nginx/CDN/静态服务器就能跑，不需要 Node 运行时。

Q4 · 工具分工

  • 类型检查
  • 文件打包压缩
  • 启动开发服务器
  • 安装依赖
tsc 管类型检查（Vite 的 esbuild 只转译不检查），vite build 管打包。类型安全来自 tsc，产物来自 Vite——两件事，两个工具。
