tRPC：端到端类型安全

最"TS 特色"的概念：没有 REST 的 URL/序列化边界，前后端共享 router 类型后，调后端函数就像调本地函数——改后端签名，前端编译期报错。这是你 Monorepo 共享类型思想的极致。

⏱ 15-20 分钟

问题：REST 的类型断层

你熟悉的 REST/HTTP 世界有个类型断层：

// 后端定义了类型安全的路由处理
GET /api/users/:id → User

// 前端却是裸字符串 + 手写类型——两边各写一份，靠约定同步
const res = await fetch(`/api/users/${id}`);
const user = await res.json() as User;  // as 断言：相信约定（第 2 课）
全新概念 tRPC：前后端共享同一份 router 定义（类型即契约）——后端实现它，前端从它推导类型。没有 URL、没有手写接口定义、没有序列化边界：类型是唯一的 API 契约。

核心：router / procedure / query / mutation

// router.ts —— 前后端共享的 API 定义（一个文件）
import { initTRPC } from "@trpc/server";
import { z } from "zod";

const t = initTRPC.create();

export const appRouter = t.router({
  // query：读操作（≈ GET）
  getTodos: t.procedure.query(() => todos),

  // mutation：写操作（≈ POST/PATCH），input 用 Zod 校验（第 18 课）
  addTodo: t.procedure
    .input(z.object({ title: z.string().min(1) }))
    .mutation(({ input }) => { return createTodo(input); }),

  toggleTodo: t.procedure
    .input(z.number())
    .mutation(({ input }) => { return toggle(input); }),
});

// 导出类型——前端只 import 这个（类型零运行时成本，第 9 课）
export type AppRouter = typeof appRouter;
tRPCREST（你的已知）
t.procedure.queryGET /endpoint
t.procedure.mutationPOST/PATCH/DELETE /endpoint
.input(zodSchema)请求体校验（手写）
类型：共享 AppRouter 自动推导手写 DTO + as 断言 + 维护文档

端到端类型安全（实测演示）

// client.ts —— 前端调用：像调本地函数
import { createTRPCProxyClient, httpBatchLink } from "@trpc/client";
import type { AppRouter } from "./router";  // 只 import 类型！

const trpc = createTRPCProxyClient<AppRouter>({
  links: [httpBatchLink({ url: "http://localhost:3003" })],
});

const list = await trpc.getTodos.query();        // 返回类型自动推导
const added = await trpc.addTodo.mutate({ title: "端到端类型安全" });

铁证：改 input 类型 → 前端编译期报错

把 client 里的 { title: "..." } 改成 { title: 42 }：

$ npx tsc --noEmit
src/client.ts(16,45): error TS2322: Type 'number' is not assignable to type 'string'.
——前端在编译期就知道后端要 string。没有任何运行时检查参与。
全新概念 端到端（end-to-end）：类型安全从后端数据库一路穿到前端组件。改后端 addTodo 的 input 或返回类型 → 前端所有用到它的地方编译期报错。对比 REST：改了后端，前端要等运行时才发现（或者永远不发现）。

React 集成（完整应用里的样子）

// App.tsx —— @trpc/react-query 的 hooks（≈ 自动的数据获取层）
const { data: todos } = trpc.getTodos.useQuery();         // 自动类型 + 缓存
const add = trpc.addTodo.useMutation();                  // 变更 hook

// 调用时类型检查、完成后自动失效缓存：
add.mutate({ title: newTitle }, { onSuccess: () => utils.getTodos.invalidate() });
这是 tRPC + React Query 的组合：useQuery 自动管理数据获取/缓存/重试，类型全部自动。配合 SSE/WebSocket 可以做成实时应用（第 15 课看板 + tRPC = 常见的 agent 平台组合）。

检查你的理解

Q1 · tRPC 定位

  • 端到端类型安全
  • 更快的打包速度
  • 自动数据库迁移
  • 内置用户认证
tRPC 让前后端共享同一份类型定义——类型是唯一的 API 契约，改后端前端编译期感知。打包/数据库/认证都不是它的职责。

Q2 · 类型来源

  • import 共享的 router 类型
  • 手写接口定义文件
  • 运行时反射获取
  • 代码生成工具生成
client 用 import type { AppRouter } 从共享 router 推导——零运行时成本（第 9 课 import type）。没有手写 DTO、没有代码生成。

Q3 · 输入校验

  • Zod schema
  • 手写 if 判断
  • JSON Schema 文件
  • 数据库约束
tRPC 与 Zod 深度集成：.input(z.object({...})) 同时提供运行时校验（第 18 课）和编译期类型。

Q4 · 变更传播

  • 编译期报错提醒
  • 运行时才报错
  • 自动忽略不匹配
  • 整个程序崩溃
前后端共享类型 → 后端签名一变，前端所有使用点编译期报错——这是端到端类型安全最直接的价值（对比 REST 的运行时才发现）。
