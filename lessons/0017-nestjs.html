NestJS：ASP.NET 的 TypeScript 版

你是 C# 开发者——NestJS 会给你"回家"的感觉：模块、控制器、服务、依赖注入、装饰器，全是 ASP.NET 的心智模型。差异化的部分：装饰器如何驱动 DI、管道校验、以及一个用 tsx 跑会踩的大坑。

⏱ 15-20 分钟

NestJS 是什么：C# 架构的 TS 移植

全新概念 NestJS：Node 生态里最"企业级"的框架——它把 ASP.NET/Spring 的架构（模块化、依赖注入、装饰器/属性、管道、守卫、拦截器）搬到了 TypeScript 上。Express/Fastify 是自由派（自己搭结构），NestJS 是"框架派"（结构内置）。

四个核心文件（真实代码，已验证）

// 1. 服务：业务逻辑（≈ DI 注册的服务类）
@Injectable()  // 装饰器声明"可注入"
export class TodosService {
  private todos: Todo[] = [];
  create(title: string): Todo { ... }
}

// 2. 控制器：路由 + 参数绑定（≈ [ApiController]）
@Controller("todos")
export class TodosController {
  constructor(private readonly service: TodosService) {}  // 构造注入

  @Get()  // GET /todos
  list() { return this.service.list(); }

  @Post()  // POST /todos（@Body() ≈ [FromBody]）
  create(@Body() dto: CreateTodoDto) {
    return this.service.create(dto.title);
  }
}

// 3. 模块：把控制器和服务组装（≈ Program.cs 注册区）
@Module({
  controllers: [TodosController],
  providers: [TodosService],  // ≈ services.AddScoped<TodosService>()
})
export class AppModule {}

// 4. 入口（≈ Program.cs）
const app = await NestFactory.create(AppModule);
app.enableCors();
await app.listen(3002);

差异点 1：装饰器驱动的 DI（vs C# 的容器配置）

全新概念 C# 的 DI 是在容器里配置（services.AddScoped<TodosService>()）；NestJS 的 DI 是声明式的——类上用 @Injectable() 标记、构造参数写类型、容器自动解析。你不写 AddScoped，只要 @Module({ providers: [...] }) 注册即可。

差异点 2：⚠️ tsx/esbuild 跑 NestJS 会注入失败（实测坑）

设计时类型元数据（design:paramtypes）：NestJS 的构造注入靠 TypeScript 编译时发出的参数类型元数据。tsc 会发出，但 esbuild（tsx 底层）不发出——所以用 tsx src/main.ts 跑 NestJS，所有注入的服务都是 undefined，API 返回 500。实测错误： TypeError: Cannot read properties of undefined (reading 'list') 
// ❌ 这样跑注入会失败（esbuild 不发出元数据）
$ tsx src/main.ts
TypeError: Cannot read properties of undefined (reading 'list')

// ✅ 这样跑正常（tsc 编译发出元数据）
$ tsc && node dist/main.js
[Nest] Mapped {/todos, GET} route ... successfully started

这也是 NestJS 官方用 tsc（或 SWC+配置）而不是裸 esbuild 的原因。真实项目用 @nestjs/cli 脚手架（内部已配好）。

差异点 3：管道校验（Pipes）

NestJS 的校验哲学：DTO 用 class（不是 type）——因为管道需要运行时的类定义来做校验和元数据（呼应第 10 课"类型管不到网络输入"）：

class CreateTodoDto {
  title!: string;  // class 而非 interface——NestJS 需要运行时元数据
}

// main.ts 全局启用校验管道（≈ C# 的 ModelState 自动校验）
app.useGlobalPipes(new ValidationPipe());
// 之后 POST /todos 缺 title 字段 → 自动 400 + 错误详情

检查你的理解

Q1 · 服务与 DI

  • DI 容器注册的服务
  • 控制器类
  • 中间件
  • 数据模型
@Injectable() 标记可注入服务，在 @Module 的 providers 注册，通过构造函数注入使用——对应 C# 的 AddScoped/AddTransient 服务。

Q2 · 注入机制

  • 编译期类型元数据
  • 运行时字符串配置
  • 全局单例变量
  • 反射遍历程序集
NestJS 读 TypeScript 编译时发出的 design:paramtypes 元数据来确定构造参数类型。tsc 会发，esbuild 不发——这就是 tsx 跑 NestJS 注入失败的原因。

Q3 · tsx 的坑

  • 注入失败，API 返回 500
  • 无法识别装饰器语法
  • 内存不足崩溃
  • 端口冲突无法启动
esbuild 不发出设计时类型元数据 → 所有构造注入的服务是 undefined → 500。用 tsc 编译（或 @nestjs/cli）跑是正解。

Q4 · DTO 选择

  • 管道需要运行时元数据
  • class 语法更简洁
  • interface 无法描述字段
  • 编译器强制要求
interface 编译后消失（第 1 课类型擦除）；ValidationPipe 需要运行时能"看到"类来做校验。所以 NestJS 的 DTO 用 class + 装饰器描述规则。
