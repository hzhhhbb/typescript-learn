Lesson 0002 · 类型系统

结构类型：长得像，就是

你在 C# 里写的 class Dog : IPet，在 TypeScript 里可以完全不写——只要 Dog 的形状像 Pet，它就是 Pet。这是 TS 与 C#/Java 最根本的类型系统差异，也是新手摔得最狠的地方。

⏱ 15-20 分钟

先看一个会颠覆你直觉的例子

同样的代码意图，两个世界的规则：

C# · 名义类型 nominal
interface IPet {
  string Name { get; }
  string Speak();
}

class Dog : IPet { // ← 必须写 : IPet
  public string Name { get; }
  public string Speak() { ... }
}
TypeScript · 结构类型 structural
interface Pet {
  name: string;
  speak(): string;
}

class Dog { // ← 不需要 implements Pet
  constructor(public name: string) {}
  speak() { return "Woof!"; }
}

const pet: Pet = new Dog("Rex"); // ✓ 编译通过
全新概念 结构类型（structural typing）：两个类型是否兼容，只看它们的形状（成员的名字和类型），不看类型名、不看继承/实现声明。Dog 有 name 和 speak，形状匹配 Pet，所以 Dog 就是 Pet。
你已经知道 C#/Java 的兼容规则叫名义类型（nominal typing）：只有显式声明了继承/实现关系，两个类型才兼容。class Dog : IPet 里的 : IPet 不是装饰——它是类型系统承认关系的唯一途径。TS 把这个"唯一途径"删掉了。

为什么 TS 要这么设计？

因为 JavaScript 生态的惯用风格就是这样：开发者随手写对象字面量传数据，而不是先定义一个类再实例化。看两个真实场景：

// 场景 1：函数参数 —— 直接传"匿名对象"
function greet(pet: Pet) {
  console.log(pet.speak());
}

greet({ name: "Tom", speak: () => "Meow!" }); // ✓ 不需要任何类

// 场景 2：API 响应 —— 数据直接匹配类型
interface User {
  id: number;
  name: string;
}

const user: User = await fetch("/api/user").then(r => r.json());
// fetch 返回的是 any，但形状对就能声明为 User —— C# 里你得先写个 DTO 类再手动映射
记住这条推论（和第一课呼应）：结构匹配是编译期行为，运行时没有任何接口存在。pet instanceof Pet 是非法代码——Pet 在编译后就不存在了。你只能 pet instanceof Dog 判断真实对象。

陷阱 1：多余属性检查（excess property check）

结构类型听上去很宽松，但有一个重要的收紧规则。猜猜下面哪个报错：

// A：对象字面量带多余属性 —— 报错
const petA: Pet = { name: "Rex", speak: () => "Woof!", age: 3 }; // ✗ TS2353

// B：先赋给变量，再赋值 —— 不报错
const rex = { name: "Rex", speak: () => "Woof!", age: 3 };
const petB: Pet = rex; // ✓ 编译通过，age 被忽略

规则：对象字面量直接赋值给类型时，TS 会检查"多余属性"——因为你很可能是拼错了属性名（nam 而不是 name）。字面量是"现写现查"；而变量在声明时类型已定型，赋给 Pet 时只看必需成员是否齐全。这就是官方文档说的 excess property checking。

$ npx tsc
src/_err.ts:5:56 - error TS2353: Object literal may only specify known
properties, and 'age' does not exist in type 'Pet'.
这是全栈开发天天会遇到的坑：把 API 返回的整个对象直接塞进"瘦接口"会报 TS2353，先解构或显式挑字段再赋值。

陷阱 2：可选属性（optional property）

接口成员可以用 ? 标记为可省略：

interface Config {
  retries: number;   // 必需
  debug?: boolean;   // 可选 —— 存在时是 boolean，缺席时视为 undefined
}

const c1: Config = { retries: 3 };              // ✓ debug 可省
const c2: Config = { retries: 1, debug: true }; // ✓
const c3: Config = {};                        // ✗ TS2741 缺 retries
你已经知道 可选属性 ≈ C# 的 bool? Debug { get; set; }——但语义更接近"属性可能整个不存在"，而不是"值为 null"。访问缺席的可选属性得到 undefined，不是 null（null/undefined 的区别我们后课讲）。

检查你的理解

Q1 · 结构 vs 名义

  • 编译通过，形状匹配即可
  • 编译失败，必须显式 implements
  • 编译失败，类不能赋给接口
  • 编译通过，但运行时抛异常
结构类型只看形状：Dog 有 name 和 speak，就兼容 Pet。implements 在 TS 里是可选的（写了也只是文档化意图 + 编译期校验，不影响兼容性）。C# 的规则在这里不适用。

Q2 · 多余属性检查

  • A 报错，B 通过
  • A 通过，B 报错
  • 两行都报错
  • 两行都通过
对象字面量直接赋值会触发多余属性检查（TS2353）；先赋给变量则只检查必需成员是否齐全。这是故意的不对称——字面量里多出的属性几乎总是拼写错误。

Q3 · 可选属性

  • 编译失败，缺少必需 retries
  • 编译通过，可选属性可省略
  • 编译通过，空对象总是合法
  • 编译失败，缺少 debug 属性
可选属性（debug?）可以省，必需属性（retries）不能省——否则 TS2741。`?` 只豁免标记了它的成员，不会豁免整个对象。

Q4 · 编译期 vs 运行时

  • 编译期检查，运行时无接口
  • 运行时检查，编译期不查
  • 编译期运行时都检查
  • 编译期运行时都不检查
呼应第一课：类型（包括接口）在编译后全部擦除。pet instanceof Pet 连编译都过不了。结构匹配是编译期给程序员的保护，不是运行时的机制。
