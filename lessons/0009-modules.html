Lesson 0009 · 工程实践（合并版）

模块系统与工程配置

把模块语法和 tsconfig 配置合成一课——因为它们是同一件事的两面：import/export 怎么写（语法），module/target/paths 怎么配（配置）。学完这课，你能看懂任何真实项目的 tsconfig.json，也知道怎么从零配一个。

⏱ 25-30 分钟（两部分可分段学）

第一部分：模块语法

模块 vs 脚本

一个 .ts 文件只有两种身份：

类型判定条件作用域
模块（module）文件里有 import 或 export自己的作用域，内部声明对外不可见
脚本（script）没有任何 import/export全局作用域，声明对所有文件可见
这是第五课示例文件加 export {} 的原因：unions.ts 和 generics.ts 都没有 import/export → 都是脚本 → 都声明了 s → 全局冲突。export {} 是"空导出"，让文件升级成模块但什么都不导出。

export：命名导出 vs 默认导出

// math.ts —— 被导入的模块
export function add(a: number, b: number): number { return a + b; }
export const PI = 3.14159;   // 命名导出：任意多个，按名字取

export default function log(msg: string): void { ... }  // 默认导出：最多一个，导入时任意起名

import：三种导入方式

// 1. 命名导入 + 默认导入（默认导入任意起名：log）
import log, { add, PI } from "./math";

// 2. 通配符导入：整个模块当命名空间对象用
import * as math from "./math";

// 3. import type：只导入类型（interface/type 别名）
import type { User } from "./types";
C#（你的已知）TypeScript（新的）
using System.Linq; 导入命名空间import { add } from "./math" 导入模块成员
namespace X { ... } 组织代码一个文件 = 一个模块（无 namespace 关键字，文件路径即身份）
项目引用 / NuGet 包import 包名（来自 node_modules）

import type 与导入省略（import elision）

一个反直觉但重要的事实：默认配置下，去掉 type 关键字产物没有区别。TS 有导入省略（import elision）机制——编译器分析出导入只用于类型位置时，自动删掉整个 import，不管你有没有写 type。两种写法我实际编译验证过：
写法 A：import type
// main.ts 源码
import type { User } from "./types";

// dist/main.js 产物
// （没有 require("./types")）
// import 被完全擦除
写法 B：去掉 type
// main.ts 源码
import { User } from "./types";

// dist/main.js 产物
// （同样没有 require("./types")）
// User 只用于类型 → 自动省略

import type 的真实价值：① 显式意图（读代码的人一眼知道是类型）；② 单文件编译器（esbuild/Babel/SWC 不做跨文件分析，import type 是它们删除类型导入的唯一依据——现代构建工具几乎都用）；③ ESM + verbatimModuleSyntax 下强制要求。

第二部分：tsconfig 深入

你现在已经认识 tsconfig 了。这部分的三个主角——target、module、paths——决定了你的项目"是什么形态"。

target：产物 JS 的语法版本

target 决定编译产物使用哪个版本的 JS 语法。同一个源码，不同 target 的产物差异巨大——我实测过：

target: ES2017（现代语法原样保留）
// 源码
async function fetchData() { return 1; }

// 产物
async function fetchData() { return 1; }
target: ES2016（转译为辅助代码）
// 同一源码，产物变成：
var __awaiter = ... // 一大坨生成器辅助函数
function fetchData() {
  return __awaiter(this, void 0, void 0,
    function* () { return 1; });
}
环境事实 你的 TypeScript 7 已移除 ES3/ES5 等老目标（最低约 ES2015）。现代项目一般配 ES2022 或 ESNext——因为目标运行环境（现代 Node/浏览器）都支持最新语法，没必要转译。只有在需要兼容老浏览器时才降低 target。

module + package.json type：CJS 还是 ESM

TS 源码都写标准 ESM 语法，产物格式由两个东西共同决定：

配置取值产物
module: "commonjs"Node 传统require() / module.exports
module: "esnext" + package.json type: "module"浏览器 / 现代 Nodeimport / export 原样保留
// math.ts 编译为 commonjs → dist/math.js：
"use strict";
Object.defineProperty(exports, "__esModule", { value: true });
exports.add = add;       // 命名导出 → exports.add
exports.default = log;   // 默认导出 → exports.default
你已经知道 类似 C# 编译成 IL + 程序集：TS 的 import/export 会编译成对应模块格式。exports.add = add 相当于"把 add 放进公开 API"。你写源码（ESM 语法）为主，产物格式由工具链决定。

paths：路径别名（全栈经典坑）

paths 让你用 @/xxx 代替一长串相对路径 ../../../../xxx：

// tsconfig.json
{ "compilerOptions": { "paths": { "@/*": ["./src/*"] } } }

// main.ts 里
import { add } from "@/math";   // 代替 ../../src/math
坑：paths 只是编译期/工具层概念。我实测过：tsc 编译通过，但产物里原样保留 require("@/math")——Node 运行时不认识 @/，直接报 "Cannot find module"。要让运行时也认识，需要 tsx / ts-node（开发）或构建工具（Vite/Webpack，打包时重写路径）。配了 paths 却忘了运行时处理，是最常见的工程化事故之一。

strict 家族：一句话总结

开关作用你的对应物
strictNullChecksnull/undefined 不能赋给普通类型（第四课）C# Nullable enable
noImplicitAny参数/变量类型不能是"隐式 any"（写了 any 或推断出 any 要显式声明）（无直接对应）
strictPropertyInitialization类属性必须在构造时初始化（否则报错）C# 字段必须初始化（可空时写 ?）
noUncheckedIndexedAccess索引访问 arr[i] 类型是 T | undefined（TS 4.1+）C# 数组越界在运行时
不用背清单：strict: true 一次打开全部。真实项目里你几乎只会遇到 strictNullChecks 和 noImplicitAny 的报错，其余默默保护你。

其他常用选项（快速过）

选项作用
outDir / rootDir产物输出目录 / 源码根目录（你的 dist/ 和 src/）
include编译哪些文件（你的 ["src"]）
lib可用的全局类型库：ES2022、DOM（浏览器 API：document、fetch 等）
types显式加载的 @types 包（你的 ["node"]，提供 process 等）
sourceMap调试映射：让浏览器/VS Code 能断点到 TS 源码（而不是编译后的 JS）
declaration生成 .d.ts 类型声明文件（发布库时才需要）

npm scripts：把命令变成按钮

package.json 的 scripts 字段给常用命令起名字（≈ C# 项目里的构建任务）：

// package.json
{
  "scripts": {
    "build": "tsc",             // npm run build → 编译
    "start": "node dist/main.js", // npm start → 运行
    "dev": "tsc --watch"       // npm run dev → 监听改文件自动重编译
  }
}

动手练习

在 code/ 里验证（8 分钟，可挑着做）

文件：src/math.ts（被导入）、src/types.ts（纯类型）、src/main.ts（入口）。做几件事：

  1. 运行 npm run build && npm start（scripts 已配好），看输出。
  2. 挑战 1：打开 dist/math.js，找到 exports.add / exports.default——确认 import/export 变成了 require/module.exports。
  3. 挑战 2：把 import type { User } 改成 import { User } 编译，grep types dist/main.js——产物一模一样（导入省略）。改回来。
  4. 挑战 3（推荐）：把 tsconfig 的 target 改成 ES2016，编译后打开 dist 里任意含 async 的文件，看一大坨 __awaiter 转译代码——再改回 ES2022。亲眼理解 target 是干什么的。
  5. 挑战 4（可选）：在 tsconfig 加 "paths": { "@/*": ["./src/*"] }，把 main.ts 的导入改成 @/math，编译——通过！但 npm start 会报 Cannot find module——亲身体验 paths 的坑，然后删掉恢复。

检查你的理解

Q1 · 模块 vs 脚本

  • 脚本，声明全局可见
  • 自动成为独立模块
  • 无法被编译
  • 必须有 export {} 才能用
没有 import/export 的文件是脚本：声明进入全局作用域。加 export {} 或任何 import/export 都能升级为模块。

Q2 · 类型导入

  • 只导入类型，无运行时代码
  • 同时导入值和类型
  • 导入整个文件的全部导出
  • 声明一个新的类型
import type 只导入类型。注意：默认 tsconfig 下普通 import 类型也会被自动省略（import elision）——type 的价值是显式意图 + esbuild/Babel 单文件编译器下的保证。

Q3 · target

  • 产物 JS 的语法版本
  • 模块的加载方式
  • 类型检查的严格度
  • 打包后的文件大小
target 决定产物用哪个版本的 JS 语法：低 target 会把 async/await 转译成辅助代码，高 target 原样保留。现代项目配 ES2022/ESNext（TS 7 已移除 ES5 等老目标）。

Q4 · paths 别名

  • 无法解析，需构建工具
  • 自动转成相对路径
  • 运行时动态解析
  • 编译时直接报错
paths 是编译期/工具层概念：tsc 编译通过但产物保留 require("@/math")，Node 不认。需要 tsx/ts-node（开发）或构建工具（打包时重写路径）。配了 paths 忘处理运行时 = 常见工程事故。

Q5 · 默认导出

  • 不能，只能有一个
  • 可以，数量不限
  • 可以，但只能有两个
  • 默认与命名导出互斥
一个模块最多一个 export default（导入时它没有名字，多个会歧义）。命名导出不限数量，两者可共存。
