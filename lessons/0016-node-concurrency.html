Node 并发模型：worker_threads 与流

第 13 课画过一条红线：CPU 密集任务会阻塞事件循环。这课给你翻越红线的工具——worker_threads（Node 的"线程"，但和 C# 线程差异大得反直觉），以及流（Streams，处理大数据的内存正解）。

⏱ 15-20 分钟

红线回顾：为什么需要 worker

第 13 课的实验：10 亿次循环让事件循环中断 975ms——所有请求一起卡住。Node 的解法不是"线程池"（那是 C# 的思路），而是：

全新概念 worker_threads：Node 的"线程"。但它的心智模型和 C# 线程完全相反：
  • C#：共享内存线程 + 锁同步
  • Node：每个 worker 是独立的 V8 实例（自己的堆、自己的事件循环），通信靠消息传递

worker_threads：独立世界 + 消息传递

// main.ts —— 主线程
import { Worker } from "node:worker_threads";

// 启动 worker：给它初始数据（workerData）
const worker = new Worker(join(__dirname, "fib-worker.js"), {
  workerData: 35,
});

worker.on("message", (result) => console.log("结果:", result));  // 收消息
// fib-worker.js —— worker 线程（独立的 V8 实例）
import { parentPort, workerData } from "node:worker_threads";

function fib(n) { return n <= 1 ? n : fib(n - 1) + fib(n - 2); }
parentPort?.postMessage(fib(workerData));  // 消息传递：结果发回主线程
$ node dist/worker-demo/main.js
主线程：启动 CPU 密集任务到 worker（fib(35)）…
[worker] 开始计算 fib(35)…
主线程收到 worker 结果: fib(35) = 9227465
  主线程 tick 1 —— 事件循环正常！   ← 关键：worker 计算期间
  主线程 tick 2 —— 事件循环正常！      主线程定时器照常走
  ...（10 次 tick 全程正常）
全新概念 消息传递 vs 共享内存：worker 之间没有共享变量——数据通过 postMessage 传递（结构化克隆：值拷贝）。需要共享大数据时用 SharedArrayBuffer（低级、要小心，很少用）。对比 C# 的 lock/Monitor/ConcurrentDictionary——Node 模型天然避开死锁和数据竞争，代价是通信要显式。

三兄弟：worker_threads vs cluster vs child_process

工具是什么用途C# 对照
worker_threads进程内线程（独立 V8）CPU 密集计算（图片处理、加密、大循环）Thread / Task.Run
cluster多进程共享一个端口（自带负载均衡）多核机器上横向利用 CPU（每个核一个进程）多实例部署
child_process独立进程（exec/spawn/fork）跑外部程序、隔离崩溃、ffmpeg 等Process.Start
决策顺序：I/O 密集（绝大多数场景）→ 不需要任何线程，异步就够；CPU 密集 → worker_threads；要利用多核跑整个服务 → cluster（或干脆多实例部署 + 负载均衡）。

Streams：处理大数据的内存正解

还记得第 13 课你问的"大文件读取性能问题"吗？流（Stream）就是那个正解——边读边处理，内存恒定：

import { createReadStream, createWriteStream } from "node:fs";
import { Transform } from "node:stream";

// 管道：读（64KB/块）→ 变换（转大写）→ 写
// 任意时刻只有一块 chunk 在内存里——不管文件是 5MB 还是 5GB
const upper = new Transform({
  transform(chunk, _enc, cb) {
    cb(null, chunk.toString().toUpperCase());
  },
});

createReadStream("big.txt", { highWaterMark: 64 * 1024 })
  .pipe(upper)
  .pipe(createWriteStream("big-upper.txt"));
全新概念 背压（backpressure）：消费者处理慢时，流会自动暂停上游（读写速率自动匹配）。.pipe() 处理背压；readFile 一次性读入整文件则没有这个概念——大数据场景（大文件、HTTP 流、日志）用流是唯一正解。
Node StreamC# 对照
Readable / Writable / TransformStreamReader / StreamWriter（概念类似）
.pipe() 管道 + 背压CopyToAsync（但无内置背压语义）
chunk 是 Buffer（二进制）ReadOnlyMemory<byte>

检查你的理解

Q1 · worker 心智模型

  • 独立 V8，消息传递通信
  • 共享内存加锁同步
  • 每个请求一个线程
  • 自动线程池调度
每个 worker 是独立 V8 实例（自己的堆和事件循环），通信靠 postMessage 消息传递（结构化克隆）。没有共享变量 → 没有死锁和数据竞争，但通信要显式。

Q2 · 使用场景

  • CPU 密集计算
  • 普通数据库查询
  • 等待外部 HTTP 响应
  • 文件流式处理
worker_threads 专治 CPU 密集（阻塞事件循环的红线）。I/O 密集（数据库、HTTP、文件）用异步就够了——不需要线程。

Q3 · Streams

  • 内存恒定不随文件大小增长
  • 速度一定比 readFile 快
  • 自动压缩文件体积
  • 不需要创建临时文件
流边读边处理，任意时刻只有一小块 chunk 在内存——5MB 和 5GB 文件内存占用相同。背压自动调节读写速率。

Q4 · 背压

  • 消费者慢时暂停上游
  • 加快消费者的处理速度
  • 压缩传输的数据
  • 加密数据传输
消费者处理不过来时，流自动暂停读入（背压），读写速率自动匹配。pipe() 内置处理，避免内存无限堆积。
